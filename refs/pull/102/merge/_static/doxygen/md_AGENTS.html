Local development guide

Project and prerequisites

Scroom is a C++23 GTK 3 image viewer with dynamically loaded plugins. Use the CMake build; the root README and .gitlab-ci.yml describe the older Autotools workflow. Current build/test CI is .github/workflows/build_cmake.yml.

On the developer's PC, dependencies are already installed in standard system locations. Start with normal CMake discovery; do not copy the cloud workspace's extracted-package setup, /workspace paths, or library overrides.

The build uses a C++23 compiler, CMake, Ninja, pkg-config, Boost (thread, filesystem, chrono, program_options), GTK 3, Cairo, GLib/GThread/GModule, TIFF, and zlib. CMake FetchContent downloads pinned fmt, spdlog, and (when tests are enabled) GoogleTest revisions, even with system development packages installed; the initial configure therefore needs network access to GitHub.

Configure and compile

Run commands from the repository root. Initialize the CMake module submodule:

git submodule update --init --recursive
git describe
cmake --preset gcc-debug
cmake --build --preset gcc-debug --parallel 4

Version generation uses git describe: keep Git history and tags available. For a shallow clone, fetch full history and tags (git fetch --unshallow --tags); for a full clone missing tags, use git fetch --tags.

The preset creates cmake-build-debug/ with bin/, lib/, and compile_commands.json. Preset schema version 6 needs CMake 3.25 or newer (despite the older minimum advertised in the preset). An equivalent explicit configuration, also useful for choosing another build directory, is:

cmake -S . -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build cmake-build-debug --parallel 4

In-source builds are forbidden. Use a separate build directory when switching compilers. The clang22-libcxx-gcc13-debug preset uses Clang 22 with libstdc++, despite its name, and pins /usr/lib/gcc/x86_64-linux-gnu/13; use it only if that toolchain exists. The GCC preset is the simpler default.

Tests

Build first, then run on a desktop with a working display:

ctest --preset gcc-debug

For headless sessions, follow Linux CI and supply a virtual display:

xvfb-run -a ctest --test-dir cmake-build-debug -j2 --output-on-failure

GTK-dependent tests require a display even though these are unit tests. Xvfb also needs xauth. A cannot open display failure is an environment problem; check the display/Xvfb startup before investigating assertions.

ENABLE_GOOGLE_TEST and ENABLE_SLOW_TESTS default to ON. There are currently eight CTest entries: util_tests, threadpool_tests, memory_manager_tests, scroom_lib_tests, tiledbitmap_tests, sppipette_tests, transparentoverlay_tests, and ruler_tests. To focus on one suite:

ctest --test-dir cmake-build-debug -R '^scroom_lib_tests$' --output-on-failure

Disabling ENABLE_SLOW_TESTS removes the threadpool suite from CTest registration; it does not merely filter individual slow cases. Reconfigure to change options.

Run the application without installing

In Bash, source the generated development environment and launch the build:

source cmake-build-debug/ENVIRONMENT
cmake-build-debug/bin/scroom /absolute/path/to/image.tif

The generated file sets SCROOM_DEV_MODE and SCROOM_PLUGIN_DIRS. Development mode reads gui/scroom.glade directly from the source tree and loads plugins from the build's lib/ directory on Linux. Launching the executable without this environment instead searches the configured installation locations, which can hide new plugins or fail to find UI resources. The generated plugin path contains a deliberate bogus entry; the following build directory is the useful entry. SCROOM_PLUGIN_DIRS is colon-separated on Linux, semicolon-separated on Windows. Development mode checks whether SCROOM_DEV_MODE exists, so use unset SCROOM_DEV_MODE to disable it rather than assigning 0.

scroom --help lists command-line options. A useful manual smoke test is to open a small PPM or TIFF, confirm the image and loaded-plugin log, then exercise zoom, pan, and the UI feature being changed. For headless startup checks, use xvfb-run -a with the development environment active; the GUI keeps running until closed, so a timeout alone does not prove that an image loaded successfully.

To test an installation without sudo, configure a user-writable prefix before building (resource/plugin paths are compiled in):

cmake -S . -B cmake-build-debug -DCMAKE_INSTALL_PREFIX="$PWD/cmake-build-debug/install"
cmake --build cmake-build-debug --parallel 4
cmake --install cmake-build-debug
(unset SCROOM_DEV_MODE SCROOM_PLUGIN_DIRS; cmake-build-debug/install/bin/scroom)

Code map and checks

  • gui/src/: startup, plugin loading, GTK callbacks, and views; gui/scroom.glade: UI; gui/ruler/: ruler widget and tests.
  • libs/: utility/context types, threadpool, memory manager, tiled bitmap, shared viewer logic, and plugin interfaces. Public headers live under the corresponding library's inc/scroom/ directory.
  • plugins/: image loaders (TIFF/PNM), overlays, measurement, pipette, metadata, and colormap tools. Tests generally live alongside their component.
  • External/: system dependency discovery and pinned FetchContent declarations.

For code changes, build and run the relevant suite, then the full suite when shared libraries or interfaces change. Match existing formatting. CI uses clang-format-22 via build_scripts/clang-format and cmake-format via build_scripts/cmake-format; both scripts modify files and require GNU parallel. Prefer formatting only touched files to avoid unrelated changes (the C++ script recursively scans the current directory). Do not commit build outputs or edit the cmake-modules submodule for ordinary application changes.

Cloud findings to retain

The existing cloud setup built Debug with GCC and previously recorded all eight CTest suites passing. Its GUI smoke check opened a generated 16-by-16 PPM under Xvfb, verified the window title, and checked the bitmap dimensions in the log. Those results establish a useful baseline, not a substitute for verifying later changes. Cloud dependencies were extracted into a custom prefix because sudo was unavailable; those prefix, pkg-config, and TIFF overrides are specific to that environment and should not be needed on the local PC.
